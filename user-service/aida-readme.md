# PART I — SERVICE DEFINITION

## 1. Purpose and Responsibilities

The User Service is responsible for managing user profiles and user-related information within the NextMinds platform.

It owns the user profile domain and provides APIs for managing personal profile information, profile visibility, profile completion, and user preferences.

The User Service is a separate microservice with its own database and business responsibilities.

It must not become a second authentication service or a general-purpose storage location for information owned by other business domains.

### 1.1 Core Responsibilities

The service is responsible for:

1. User profile creation.
2. User profile retrieval.
3. User profile modification.
4. User profile information validation.
5. Profile completion tracking.
6. Profile visibility and privacy settings.
7. User preferences.
8. User-specific application settings.
9. Providing permitted user profile information to other services.
10. Managing profile-related lifecycle operations.
11. Supporting administrative profile management.
12. Maintaining consistency of profile information.

### 1.2 Responsibilities Outside This Service

The following responsibilities belong to other services:

- Authentication.
- Registration and login.
- Password management.
- Password hashing.
- Access token generation.
- Refresh token management.
- Role management.
- Permission management.
- School management.
- Classroom management.
- Educational content.
- Marketplace functionality.
- Payment management.
- Notification delivery.

These responsibilities must not be implemented inside User Service.

# PART II — MICROSERVICE BOUNDARIES

## 2. User Service vs Auth Service

The separation between Auth Service and User Service is a fundamental architectural requirement.

### 2.1 Auth Service Owns

Auth Service is the source of truth for:

- User identity.
- User UUID.
- Login identifiers.
- Email and phone authentication identifiers.
- Password credentials.
- Password hashes.
- Authentication status.
- Access tokens.
- Refresh tokens.
- Roles.
- Authentication-related permissions.
- Login history.
- Password reset operations.
- Authentication lifecycle.

### 2.2 User Service Owns

User Service is the source of truth for:

- First name.
- Last name.
- Display name.
- Profile image reference.
- Birth date.
- Profile information.
- Profile visibility.
- Profile completion.
- User preferences.
- Profile-specific settings.

### 2.3 Ownership Rules

1. User Service must never generate an independent user identity.
2. The profile UUID must be identical to the UUID generated by Auth Service.
3. User Service must not store password hashes.
4. User Service must not store refresh tokens.
5. User Service must not manage roles.
6. User Service must not directly access the Auth database.
7. User Service must not create cross-database foreign keys to Auth tables.
8. User Service must not independently decide whether an account is authenticated.
9. Authentication-related identifiers must not be duplicated without an explicit business requirement.
10. Any future communication with Auth must happen through a defined API or integration contract.

### 2.4 Important Distinction: User Profile vs User Role

A user's business identity and authorization role are different concepts.

For example:

- A person may be a student.
- A person may be a parent.
- A person may be a school representative.
- A person may be an administrator.

These concepts must not automatically be treated as equivalent.

Auth Service owns authorization roles.

User Service owns profile information.

Business relationships such as parent-child relationships, student-school relationships, and school memberships must be modeled in the appropriate business domain.

Do not introduce these relationships into User Service merely because they involve users.

# PART III — PRODUCT AND DOMAIN ANALYSIS

## 3. NextMinds User Domain

NextMinds is intended to serve different participants in an educational ecosystem, including students, parents, and schools.

Therefore, the User Service must be designed to support different user experiences without introducing unnecessary coupling to future business services.

### 3.1 Individual User Profile

An individual user may have:

- Personal information.
- Display information.
- Profile image.
- Profile preferences.
- Privacy preferences.
- Profile completion information.

### 3.2 Student and Parent Accounts

The User Service may eventually provide profile information for students and parents.

However:

- Student academic information does not belong here.
- Parent-child relationships do not automatically belong here.
- School enrollment information does not belong here.
- Educational records do not belong here.

These concepts require their own domain analysis and may belong to future services.

### 3.3 School-Related Accounts

A school may interact with NextMinds through one or more user accounts.

The following distinction must be preserved:

- A user account represents an authenticated identity.
- A school represents a business or organizational entity.
- A school representative is a user associated with a school.

Do not model a school as an ordinary user profile.

Do not store school business information inside User Service.

The relationship between school accounts and school entities must be defined when the School domain is designed.

### 3.4 Open Domain Decisions

The following questions must be resolved during domain analysis:

1. Can one person have multiple profiles?
2. Can one user represent multiple schools?
3. Can a parent also have a student account?
4. Can one account have multiple business identities?
5. Are student and parent classifications stored in User Service or another domain?
6. Can users make their profiles publicly visible?
7. Which profile fields are visible to other users?
8. Which profile fields are visible only to the owner?
9. Does a user need a completed profile before accessing the platform?
10. Which information is mandatory during initial onboarding?

Do not invent answers to these questions.

Document the decisions before implementing the affected domain components.

# PART IV — DOMAIN MODEL

## 4. Initial Domain Entities

The initial domain should remain small and focused.

The following entities are proposed.

## 4.1 UserProfile

Represents the personal profile associated with an Auth user identity.

Proposed attributes:

| Field | Type | Description |
|---|---|---|
| id | UUID | Same UUID as Auth user |
| firstName | String | User's first name |
| lastName | String | User's last name |
| displayName | String | Display name |
| avatarReference | String | Profile image reference |
| birthDate | LocalDate | Date of birth |
| createdAt | Instant | Creation timestamp |
| updatedAt | Instant | Last update timestamp |
| version | Long | Optional optimistic locking version |

### Field Rules

**id**
- Primary key.
- UUID.
- Must be received from the authenticated identity.
- Must never be generated independently by User Service.

**firstName**
- Maximum length must be defined.
- Must be validated.
- Mandatory status requires a product decision.

**lastName**
- Maximum length must be defined.
- Must be validated.
- Mandatory status requires a product decision.

**displayName**
- May be used instead of showing the legal or full name.
- Must have a defined length limit.
- Its fallback behavior must be documented.

**avatarReference**
- Stores an image reference, URL, or storage key.
- Does not store image binary data.
- File upload infrastructure is outside the initial scope.

**birthDate**
- Uses a date-only representation.
- Must not accept future dates.
- Must not be mandatory unless the product requires it.
- Must be treated as personal information.

**createdAt**
- Set when the profile is created.
- Must not be editable by clients.

**updatedAt**
- Updated whenever profile information changes.
- Must not be editable by clients.

**version**
- May be used for optimistic locking.
- Prevents silent overwriting of concurrent changes.
- Include it only if the chosen update strategy requires it.

### 4.1.1 Important Restrictions

Do not add the following fields without explicit requirements:

- National ID.
- Home address.
- Gender.
- Marital status.
- School information.
- Academic information.
- Parent information.
- Student information.
- Payment information.
- Authentication credentials.

These fields either contain sensitive information or belong to other domains.

This entity belongs to a later development phase.

Potential fields:

| Field | Description |
|---|---|
| id | Preference record identifier |
| userId | Associated user UUID |
| locale | Preferred application language |
| timezone | User timezone |
| theme | Application appearance preference |
| createdAt | Creation timestamp |
| updatedAt | Last modification timestamp |

The exact fields must be based on product requirements.

Do not implement every possible preference in the initial version.

---

## 4.3 ProfileVisibility

Represents visibility rules for profile information.

This concept may be implemented as fields within UserProfile or as a separate entity depending on the final privacy requirements.

Potential visibility levels:

- PRIVATE
- PUBLIC
- AUTHENTICATED_USERS

Do not assume that every profile must be publicly accessible.

Visibility must be enforced on the server side.

A client-side decision to hide information is not a security mechanism.

---

## 4.4 Profile Completion

Profile completion represents whether the required profile information has been provided.

Completion must be calculated using explicit business rules.

For example:

- First name exists.
- Last name exists.
- Required profile fields are valid.

The exact required fields must be determined by product requirements.

Avoid storing a manually maintained boolean such as `isComplete` unless there is a clear reason.

A stored completion flag can become inconsistent when profile fields change.

Prefer a centralized completion calculation.

# PART V — DATABASE DESIGN

## 5. Database Ownership

User Service must own an independent PostgreSQL database.

Suggested database name:

`nextminds_user`

The exact database name must follow the existing Docker Compose and environment naming conventions.

### 5.1 Initial Table: user_profiles

Proposed structure:

| Column | Type | Constraints |
|---|---|---|
| id | UUID | Primary Key |
| first_name | VARCHAR | Nullable status TBD |
| last_name | VARCHAR | Nullable status TBD |
| display_name | VARCHAR | Nullable |
| avatar_reference | VARCHAR | Nullable |
| birth_date | DATE | Nullable |
| created_at | TIMESTAMP WITH TIME ZONE | Not Null |
| updated_at | TIMESTAMP WITH TIME ZONE | Not Null |
| version | BIGINT | Optional |

### 5.2 Database Constraints

- UUID must be the primary key.
- Required fields must have appropriate NOT NULL constraints.
- String fields must have explicit length limits.
- Date constraints must be enforced where appropriate.
- Timestamps must use a consistent timezone strategy.
- Duplicate profiles for the same Auth UUID must be impossible.
- No cross-service foreign keys must be created.

### 5.3 Future Tables

Potential future tables:

- user_preferences
- profile_visibility_settings
- profile_activity
- profile_audit_history

These tables must not be created until their corresponding requirements are approved.

### 5.4 Migration Strategy

Use Liquibase exclusively for schema migrations.

Requirements:

1. Every schema change must have a Liquibase changeset.
2. Changesets must be version-controlled.
3. Changesets must follow the existing naming convention.
4. Existing database data must be preserved during schema changes.
5. Production schema must not depend on Hibernate automatic DDL generation.
6. Migration ownership belongs exclusively to User Service.
7. Do not use Flyway.

# PART VI — API DESIGN

## 6. API Standards

Base path:

`/api/v1/users`

All APIs must follow existing NextMinds conventions.

Requirements:

- RESTful resource naming.
- Correct HTTP methods.
- Consistent status codes.
- DTO-based requests and responses.
- Validation.
- Standard error responses.
- RFC 9457 Problem Details where applicable.
- JWT-based authentication.
- No direct exposure of JPA entities.

## 6.1 Current User Profile

### GET /api/v1/users/me

Purpose:

Retrieve the authenticated user's profile.

Authentication:

Required.

Input:

No user ID is accepted from the client.

The user identity must be extracted from the validated JWT according to the existing Auth token contract.

Possible responses:

- 200 OK: Profile found.
- 404 Not Found: Profile does not exist.
- 401 Unauthorized: Missing or invalid authentication.

The response must contain only fields intended for the profile owner.

### POST /api/v1/users/me

Purpose:

Create the authenticated user's profile.

Authentication:

Required.

The profile ID must come from the authenticated identity.

Request DTO:

`CreateUserProfileDTO`

Potential fields:

- firstName
- lastName
- displayName
- birthDate
- avatarReference

The client must not provide:

- id
- createdAt
- updatedAt
- version
- roles
- password
- authentication identifiers

Possible responses:

- 201 Created: Profile created.
- 400 Bad Request: Invalid request.
- 401 Unauthorized: Invalid authentication.
- 409 Conflict: Profile already exists.

The endpoint must prevent duplicate profile creation.

### PATCH /api/v1/users/me

Purpose:

Update selected profile fields.

Authentication:

Required.

Request DTO:

`UpdateUserProfileDTO`

Requirements:

- Only explicitly allowed fields may be updated.
- Omitted fields must remain unchanged.
- Null handling must be documented.
- The authenticated user owns the profile.
- The client cannot change the profile UUID.
- Immutable fields must not be editable.

Possible responses:

- 200 OK: Profile updated.
- 400 Bad Request: Invalid request.
- 401 Unauthorized.
- 404 Not Found: Profile does not exist.

PATCH behavior must be consistent and documented.

Do not accidentally replace omitted fields with null.

### GET /api/v1/users/{id}

Purpose:

Retrieve another user's permitted profile information.

This endpoint requires a separate privacy decision.

It must not return private information by default.

Only fields explicitly approved for visibility may be returned.

The endpoint must not expose:

- Authentication identifiers.
- Password-related information.
- Private preferences.
- Sensitive personal information.
- Administrative metadata.

If public profile access is not approved, do not implement this endpoint in the initial MVP.

# PART VII — SECURITY ARCHITECTURE

## 7. Authentication

User Service must operate as an OAuth2 Resource Server.

It must validate access tokens issued by Auth Service.

Expected validations:

1. JWT signature.
2. Issuer.
3. Audience.
4. Expiration.
5. Not-before timestamp, if present.
6. Required claims.
7. Token format and supported algorithm.

Use the same JWT contract as the existing NextMinds infrastructure.

Do not invent new claim names.

### 7.1 User Identity Extraction

The authenticated user UUID must be extracted from the agreed JWT claim.

The existing Auth Service token contract must determine whether the UUID is represented by `sub` or another claim.

Do not assume the claim name without confirming the actual contract.

Create a centralized mechanism for obtaining the authenticated user UUID.

Controllers must not repeatedly parse JWT claims manually.

### 7.2 Ownership Enforcement

For every self-service operation:

- The owner UUID comes from the authenticated identity.
- The client cannot select another owner.
- The service must verify ownership before modifying data.
- Repository access must use the authenticated UUID.
- User IDs in request bodies must never override the authenticated identity.

### 7.3 Authorization

Authorization must use the existing NextMinds roles and security conventions.

Auth Service owns roles.

User Service consumes the relevant authorization information from the validated token.

Potential access categories:

- Authenticated user.
- Administrative user.
- Public profile access, if approved.

Do not create roles inside User Service.

### 7.4 Security Restrictions

- Do not disable authentication globally.
- Do not trust Gateway as the only security boundary.
- Do not accept unsigned tokens.
- Do not log access tokens.
- Do not log personal information unnecessarily.
- Do not expose internal database errors.
- Do not expose private profiles through public endpoints.

# PART X — INTEGRATION

## 10. Discovery Service

Requirements:

- Use the existing Discovery Service.
- Follow existing service naming conventions.
- Use environment-based configuration.
- Avoid hardcoded infrastructure addresses.
- Follow the existing Eureka authentication configuration.
- Expose appropriate health information.

Suggested application name:

`user-service`

The actual application name must match the existing naming convention.

## 10.1 Gateway Integration

User Service must be accessible through Gateway.

Requirements:

- Define a route for User Service.
- Follow existing route naming conventions.
- Use service discovery where appropriate.
- Preserve existing JWT validation behavior.
- Apply the existing authorization policy approach.
- Do not duplicate Gateway infrastructure.
- Do not expose unnecessary internal endpoints.

The Gateway remains the primary external entry point.

## 10.2 Auth Integration

The current Auth Service owns user identity creation.

The profile creation flow is not yet finalized.

Potential approaches:

**Approach A — REST Orchestration**

An application component coordinates Auth registration and profile creation through service APIs.

**Approach B — Event-Driven Integration**

Auth publishes a user-created event, and User Service consumes it.

**Approach C — Client Orchestration**

The client completes registration and subsequently creates the user profile.

These approaches have different consistency, failure-handling, and coupling implications.

Do not implement any approach until the registration lifecycle and failure behavior have been agreed upon.

### Integration Questions

- What happens if Auth registration succeeds but profile creation fails?
- Can a user exist without a profile?
- Should profile creation be retried?
- How should duplicate creation requests be handled?
- How should account deletion affect the profile?
- What happens when an account is disabled?
- Which service owns the overall registration workflow?

These decisions must be documented before integration.

## 10.3 Inter-Service Data Access

Other services must not directly access the User Service database.

They must obtain user profile information through an explicit API or approved integration contract.

Do not introduce synchronous calls everywhere.

Only services that genuinely need profile information should depend on this integration.

# FINAL ARCHITECTURAL PRINCIPLES

The User Service must follow these principles:

1. Auth owns identity; User owns profile.
2. Each microservice owns its database.
3. No direct cross-service database access.
4. No duplicated authentication logic.
5. No duplicated role management.
6. Profile ownership comes from authenticated identity.
7. Privacy must be enforced server-side.
8. Business relationships belong to their respective domains.
9. Use Liquibase for database migrations.
10. Build only what the product currently requires.
11. Keep future capabilities extensible without implementing them prematurely.
12. Prefer explicit contracts over implicit service dependencies.

**The objective is not to build a large user-management system. The objective is to establish a reliable, secure, and extensible User domain that can support the future growth of NextMinds without violating microservice boundaries.**
