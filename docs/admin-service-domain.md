# Admin Service domain and database design

Phase 2 design for NextMinds Admin Service. This document defines the initial domain and the PostgreSQL schema. It does not add the service, entities, or Liquibase changes.

Admin Service owns administrative workflows, this audit record, and later read-only dashboard aggregation. It does not own users, administrators, roles, permissions, credentials, account status, or profiles.

The only local persistent model in the initial release is `AdminAuditLog`.

Database name, when the service is added: `nextminds_admin`. Schema: `public`. Port: `8083`. Migrations: Liquibase. No foreign keys to Auth Service or User Service.

## Domain model

`AdminAuditLog` is an append-only record of one administrative mutation. It answers who acted, what was requested, which resource was involved, when the attempt started, why it was requested, and whether it finished in success or failure.

An audit row is not an administrator, a role, or a user. `administratorId` is a copy of the JWT `sub` claim. It is not a local identity and it has no foreign key.

### Fields

| Field | Required | Description |
| --- | --- | --- |
| `id` | yes | UUID primary key. Generated by the application with the same UUID approach as Auth (`uuid` values, not a database sequence). |
| `administratorId` | yes | UUID from JWT `sub`. Immutable. |
| `action` | yes | One value from the initial action catalog. Immutable. |
| `targetType` | yes | Kind of resource the action concerns. Immutable. |
| `targetId` | depends | UUID of that resource. Null only for `ROLE_CREATED` while the result is `PENDING` or `FAILURE`. Required once that creation is `SUCCESS`, and required for every other action. |
| `reason` | depends | Administrator's justification. Immutable. See the reason rules below. |
| `result` | yes | `PENDING`, `SUCCESS`, or `FAILURE`. Starts as `PENDING`. |
| `sourceIp` | no | Client address when it is actually known. Otherwise null. |
| `correlationId` | no | Request `X-Correlation-ID` when it is a UUID. Otherwise null. |
| `metadata` | no | Small JSON object of safe operational detail. |
| `createdAt` | yes | Time the attempt was stored. Never updated. |
| `completedAt` | no | Time the result left `PENDING`. Null while pending. Set once. |

`correlationId` is not a new business concept. Auth and the gateway already use `X-Correlation-ID`. Storing it on the audit row links the security record to application logs when the final database update fails.

### Initial action catalog

These are the Auth mutations an `ROLE_ADMIN` token can perform today. Each one is audited.

| Action | Auth API | `targetType` | `targetId` at insert |
| --- | --- | --- | --- |
| `ROLE_CREATED` | `POST /api/v1/auth/admin/roles` | `ROLE` | Null while `PENDING` or `FAILURE`. The Auth role id is required before `SUCCESS`. |
| `ROLE_UPDATED` | `PUT /api/v1/auth/admin/roles/{roleId}` | `ROLE` | Role id from the path. |
| `ROLE_DELETED` | `DELETE /api/v1/auth/admin/roles/{roleId}` | `ROLE` | Role id from the path. |
| `ROLE_ASSIGNED` | `POST /api/v1/auth/admin/users/{userId}/roles` | `USER` | User id from the path. |
| `ROLE_REVOKED` | `DELETE /api/v1/auth/admin/users/{userId}/roles/{roleId}` | `USER` | User id from the path. |

`ROLE_ASSIGNED` and `ROLE_REVOKED` target the user. The role id and role name belong in `metadata`. An administrator is a user who holds `ROLE_ADMIN`, so granting that role is `ROLE_ASSIGNED`, not a separate administrator record.

Action and target type stay paired: `ROLE_CREATED`, `ROLE_UPDATED`, and `ROLE_DELETED` use `ROLE`. `ROLE_ASSIGNED` and `ROLE_REVOKED` use `USER`.

Read APIs are not in this catalog. Listing roles and reading a user's roles do not change Auth state. Auditing them would dominate the table without recording a decision.

### Future actions

Do not accept or store these until the downstream API exists. Adding one later means extending the application catalog and the database check constraint in a new Liquibase changeset.

| Action | Blocked on |
| --- | --- |
| Account status change | Auth has no status-change API. Status values remain `PENDING_VERIFICATION`, `ACTIVE`, `INACTIVE`, and `SUSPENDED`. There is no `BLOCKED`. |
| Revoke another user's sessions | `POST /api/v1/auth/logout-all` revokes only the token subject. |
| Forced password reset | Reset is self-service. No mail delivery is configured. |
| Create administrator as one operation | Public registration always assigns `ROLE_USER`. There is no create-admin API. |
| Permission create, update, or assignment | Auth has no permission model and the JWT has no permission claim. |
| Profile change | User Service has no profile API yet. Profiles, when they exist, stay under `/api/v1/users/**`. |

`USER_STATUS_CHANGE_REQUESTED` and `ADMIN_ACCOUNT_CREATED` are not initial actions. Recording a request the platform cannot perform would look like an operation that happened.

### Result lifecycle

`result` has three states:

| State | Meaning |
| --- | --- |
| `PENDING` | The attempt is stored. The downstream outcome is not recorded yet. |
| `SUCCESS` | Auth confirmed that the mutation completed. |
| `FAILURE` | Admin Service did not obtain a confirmed successful outcome. |

`SUCCESS` is written only after a successful Auth response. A validation failure inside Admin Service, before the attempt is stored, does not create a row.

`FAILURE` does not by itself mean Auth left the data unchanged. A confirmed Auth error means Auth rejected the mutation. A timeout, a dropped connection, or any other case where Admin Service cannot tell whether Auth applied the mutation is also finalized as `FAILURE`, with `metadata.downstreamOutcome` set to `UNKNOWN`. That record must not be read as proof that the business change failed. There is no fourth result state.

`completedAt` is null exactly when `result` is `PENDING`. It is set in the same update that sets `SUCCESS` or `FAILURE`. `createdAt` stays unchanged.

### Reason rules

A reason is required for operations that grant, remove, or destroy authorization:

- `ROLE_ASSIGNED`
- `ROLE_REVOKED`
- `ROLE_DELETED`

A reason is optional for `ROLE_CREATED` and `ROLE_UPDATED`.

The stored value is trimmed text, at most 500 characters. Blank text is stored as null. The reason is the administrator's words, not a copy of the request body.

The application rejects a missing or blank reason for those three actions with a validation error before it inserts the audit row and before it calls Auth. The database check `ck_admin_audit_logs_reason` rejects null, empty, and whitespace-only values for the same three actions.

### Source IP

Store an address only when it is the administrator's address.

The gateway does not set a trusted client-IP header today. `X-Forwarded-For` from the caller is spoofable, so Admin Service must not copy it. In the normal gateway path the immediate socket address is the gateway, and the column stays null.

A direct call to the service, such as local development, may store that socket address. The column is nullable. Maximum stored length is 45 characters, which covers an IPv6 address.

### Metadata rules

`metadata` is a JSON object, or null when there is nothing to store. It is written during finalization, not supplied by the client.

Allowed contents:

- Role id and role name involved in the operation.
- Previous and new role name or description for `ROLE_UPDATED`.
- Downstream service name (`auth-service`).
- HTTP status and Auth `errorCode` on failure.
- The created role id, including when it is also copied into `targetId`.

Forbidden contents:

- Passwords, password hashes, access tokens, refresh tokens, reset tokens, and private keys.
- Database credentials and any secret.
- The `Authorization` header.
- Email addresses, usernames, or other identifiers copied from credentials.
- Profile payloads, names, or avatars.
- Raw downstream response bodies.
- Stack traces.

Serialized metadata must stay small. The application limit is 4 KiB. A confirmed Auth failure stores the classification, for example `{ "downstream": "auth-service", "downstreamOutcome": "REJECTED", "httpStatus": 409, "errorCode": "ROLE_IN_USE" }`.

A timeout or any other uncertain outcome stores that the result is unknown, for example:

```json
{
  "downstreamOutcome": "UNKNOWN",
  "failureType": "TIMEOUT"
}
```

`downstreamOutcome` is `CONFIRMED` on success, `REJECTED` when Auth returned a definite error, and `UNKNOWN` when Admin Service cannot tell whether the mutation was applied.

### Invariants

1. `administratorId`, `action`, `targetType`, `reason`, `sourceIp`, `correlationId`, and `createdAt` never change after insert.
2. `targetId` may change only from null to one UUID, and only while the row is still `PENDING`. A `ROLE_CREATED` row must not be finalized as `SUCCESS` unless that UUID is the role id Auth returned.
3. `result` may change only from `PENDING` to `SUCCESS` or `FAILURE`, once.
4. `completedAt` may change only from null to one timestamp, in that same update.
5. `metadata` may be set once, in that same update. The client cannot patch it later.
6. A row is never deleted through an administrative API.
7. No downstream mutation starts unless the `PENDING` insert has committed.
8. The HTTP response follows the Auth outcome. It does not claim a rollback because the audit update failed.

## Audit lifecycle

1. Authenticate the bearer token and require `ROLE_ADMIN`.
2. Validate the command, including a required reason where the catalog demands one.
3. Insert the audit row as `PENDING` and commit it.
4. Call Auth with the same administrator bearer token.
5. Update that row to `SUCCESS` or `FAILURE`, set `completedAt`, set `metadata`, and, for a successful `ROLE_CREATED`, set `targetId` to the role id Auth returned. Do not write `SUCCESS` for role creation when that id is missing.
6. Return Auth's result to the client.

There is no message broker and no distributed transaction. The audit update is a second local commit.

### Scenario A — the attempt cannot be stored

Do not call Auth. The client receives an error. Nothing changed in Auth, and there is no audit row.

### Scenario B — Auth fails, or the outcome is unknown

When Auth returns a definite error, update the row to `FAILURE` with `downstreamOutcome` `REJECTED`, plus the Auth status and `errorCode`. Return that failure to the client.

When the call times out, the connection drops, or Admin Service otherwise cannot tell whether Auth applied the mutation, finalize the row as `FAILURE` once Admin Service knows the call has ended. Metadata records `downstreamOutcome` `UNKNOWN` and a `failureType` such as `TIMEOUT`. The client is told that the outcome is unknown. The response must not say the mutation definitely failed, and Admin Service must not call Auth again to retry it.

The row must not stay `PENDING` when Admin Service knows the call ended.

### Scenario C — Auth succeeds

Update the row to `SUCCESS`, then return Auth's success response. For `ROLE_CREATED`, copy the new role id into `targetId` in that same update. If Auth's success response does not include that role id, do not finalize the row as `SUCCESS`. Treat the outcome as unknown: finalize `FAILURE` with `downstreamOutcome` `UNKNOWN`, and do not retry the create.

### Scenario D — Auth succeeds, but the audit update fails

Auth's change stands. Admin Service must not describe it as rolled back and must not call Auth again to undo it.

The client still receives the successful Auth result. The application logs at error level the audit id, `correlationId`, action, and that finalization failed. The token is not logged. The row can remain `PENDING`. Operators compare that row with the error log and with Auth's logs. Repair is a manual correction of that audit row's result, not a second business call.

The same visibility rule applies when Auth fails and the failure update also fails. The client receives the Auth failure. The row may remain `PENDING`. The error log must say whether Auth succeeded or failed, so a stale `PENDING` row is not assumed to be a crash.

### Scenario E — the process stops after the insert

The row stays `PENDING` and `completedAt` stays null. Auth may or may not have applied the change.

A stuck attempt is a row with `result = PENDING` and `createdAt` older than two minutes. Two minutes is an operational threshold, well above the gateway's five-second response timeout. Nothing in the initial design scans or repairs these rows automatically. Automatic retry is unsafe: assigning the same role again returns a conflict, and a retried delete can report a different outcome from the first call.

Investigation uses the audit id, `correlationId`, action, and target. Auth's own logs are the source for whether the mutation happened.

## Database design

One table, `admin_audit_logs`. No other initial tables.

| Column | Type | Null | Notes |
| --- | --- | --- | --- |
| `id` | `uuid` | no | Primary key `pk_admin_audit_logs`. |
| `administrator_id` | `uuid` | no | Copied identity. No foreign key. |
| `action` | `varchar(64)` | no | Check constraint `ck_admin_audit_logs_action`. |
| `target_type` | `varchar(32)` | no | Check constraint `ck_admin_audit_logs_target_type`. |
| `target_id` | `uuid` | yes | Null only for `ROLE_CREATED` in `PENDING` or `FAILURE`. Required for `ROLE_CREATED` in `SUCCESS` and for every other action. |
| `reason` | `varchar(500)` | yes | Non-blank for `ROLE_ASSIGNED`, `ROLE_REVOKED`, and `ROLE_DELETED`. Check constraint `ck_admin_audit_logs_reason`. |
| `result` | `varchar(16)` | no | `PENDING`, `SUCCESS`, or `FAILURE`. |
| `source_ip` | `varchar(45)` | yes | |
| `correlation_id` | `uuid` | yes | |
| `metadata` | `jsonb` | yes | |
| `created_at` | `timestamp(6) with time zone` | no | |
| `completed_at` | `timestamp(6) with time zone` | yes | |

`timestamp(6) with time zone` matches Auth. Store UTC. Hibernate later uses `ddl-auto: validate`.

### Checks

```text
ck_admin_audit_logs_action
  action in (
    'ROLE_CREATED',
    'ROLE_UPDATED',
    'ROLE_DELETED',
    'ROLE_ASSIGNED',
    'ROLE_REVOKED'
  )

ck_admin_audit_logs_target_type
  target_type in ('ROLE', 'USER')

ck_admin_audit_logs_action_target_type
  (action in ('ROLE_CREATED', 'ROLE_UPDATED', 'ROLE_DELETED') and target_type = 'ROLE')
  or (action in ('ROLE_ASSIGNED', 'ROLE_REVOKED') and target_type = 'USER')

ck_admin_audit_logs_target_id
  target_id is not null
  or (
    action = 'ROLE_CREATED'
    and result in ('PENDING', 'FAILURE')
  )

ck_admin_audit_logs_result
  result in ('PENDING', 'SUCCESS', 'FAILURE')

ck_admin_audit_logs_completion
  (result = 'PENDING' and completed_at is null)
  or (result <> 'PENDING' and completed_at is not null)

ck_admin_audit_logs_reason
  action not in ('ROLE_ASSIGNED', 'ROLE_REVOKED', 'ROLE_DELETED')
  or (reason is not null and btrim(reason) <> '')
```

Auth stores account status as an unchecked `varchar`. These checks are tighter because this table is the security history, and the allowed actions are a closed initial set. A new action is a deliberate migration.

There is no check that can express "update `target_id` only once" without a trigger. That rule stays in the application. No triggers in the initial schema.

### Indexes

| Index | Columns | Why it exists |
| --- | --- | --- |
| `idx_admin_audit_logs_created_at` | `created_at desc` | Recent history and date-range scans. |
| `idx_admin_audit_logs_administrator_created` | `administrator_id`, `created_at desc` | One administrator's activity, newest first. |
| `idx_admin_audit_logs_target_created` | `target_type`, `target_id`, `created_at desc` | History of one role or one user. |
| `idx_admin_audit_logs_action_created` | `action`, `created_at desc` | Filter by action without sorting the whole table. |
| `idx_admin_audit_logs_result_created` | `result`, `created_at desc` | Failures, and stuck `PENDING` rows older than the threshold. |

No index on `correlation_id` yet. Lookup by that id matters after a finalization failure, which should be rare, and the column can be indexed later without a model change.

No combined indexes such as `(administrator_id, action, created_at)`. Optional filters multiply quickly, and the initial volume does not justify them.

### Relationships

None. `administrator_id` and `target_id` are identifiers owned by Auth Service. A foreign key across databases is not possible and a foreign key onto a local copy is out of scope.

## Integrity and ownership

Ordinary admin APIs expose no delete and no general edit. The only write after insert is the single finalization update described above.

The application enforces:

- who may insert (an authenticated `ROLE_ADMIN` path, not a public endpoint)
- immutability of the original attempt fields
- one transition out of `PENDING`
- metadata size and the forbidden-content rules
- required reasons, before the audit insert and before the Auth call
- a successful `ROLE_CREATED` finalization includes the role id Auth returned

The database enforces:

- primary key
- not-null columns
- lengths
- the closed action, target type, and result sets
- each action paired with its target type
- `target_id` present except for `ROLE_CREATED` while `PENDING` or `FAILURE`
- a non-blank `reason` for assign, revoke, and delete
- `completed_at` paired with a finished result

The service's database user can still change rows if someone uses it directly. The initial design does not add a restricted database role or row-security policy. Those controls can be considered when deployment credentials are split between the application and operators.

Audit rows are Admin Service data. Technical logs are a separate channel. A log line does not replace a missing audit row, and an audit row does not replace an error log when finalization fails.

## Retention and access

The initial writers are people performing role administration, not end-user traffic. Growth is low compared with Auth's credential and token tables.

Reads are paginated, newest `created_at` first, with `id` as the tie-breaker. The initial page size should follow the same bounds already sketched for User Service: default 20, maximum 100. Offset paging is enough at this volume. Keyset paging can wait until offset cost shows up.

Do not partition the table. Do not delete or archive rows to save space. A retention or archive policy needs an explicit decision later. Until that decision, history stays in `admin_audit_logs`.

## Future considerations

Out of the initial model:

- fine-grained `admin.*` permissions
- account status changes and any blocked state
- session revocation for another user
- password administration
- profile data and profile search
- schools, students, parents, and teachers
- support tickets and platform configuration
- dashboard snapshot tables
- internal notes and approval workflows
- partitioning, archival, and automatic deletion
- a background reconciler for stale `PENDING` rows
- a trusted client-IP header from the gateway

Dashboard statistics that count audit rows may read this table. They do not need a second stored model.

## Decisions made in this design

1. One table, `admin_audit_logs`. No administrator, role, user, or permission tables.
2. The live action catalog is the five role mutations Auth supports today.
3. Role assignment and revocation record the user as the target. The role id is metadata.
4. Reads are not audited.
5. Results are `PENDING`, `SUCCESS`, and `FAILURE`, with a separate `completedAt`.
6. Grant, revoke, and delete require a non-blank reason, in both the application and `ck_admin_audit_logs_reason`. Create and update do not.
7. `source_ip` is null for gateway traffic until a trusted client address exists.
8. `correlation_id` is stored so a stuck row can be matched to logs.
9. The downstream call is skipped when the attempt insert fails.
10. A successful Auth change is never reported as rolled back when audit finalization fails.
11. Stale `PENDING` rows are investigated manually. They are not retried automatically.
12. Enumerations, action and target type pairs, the `target_id` rule, required reasons, and the pending/completion pair are database check constraints. Set-once field rules stay in the application. No triggers.
13. `FAILURE` means a confirmed success was not obtained. An unknown Auth outcome is stored as `FAILURE` with `downstreamOutcome` `UNKNOWN` and is not retried.

## Open decisions

1. Confirm that gateway traffic stores a null `source_ip` in the first release, instead of changing the gateway to forward a trusted client address.
2. Confirm that read-only role APIs stay out of the audit catalog.
